```python

from datetime import datetime
from uuid import UUID, uuid4

from sqlalchemy import DateTime, ForeignKey, Uuid, func
from sqlalchemy.orm import DeclarativeBase, Mapped, MappedColumn, mapped_column


class Base(DeclarativeBase):
    pass


class UUIDPrimaryKeyMixin:
    id: Mapped[UUID] = mapped_column(
        Uuid(as_uuid=True),
        primary_key=True,
        default=uuid4,
    )


class CreatedAtMixin:
    created_at: Mapped[datetime] = mapped_column(
        DateTime(timezone=True),
        server_default=func.now(),
    )


class TimestampMixin(CreatedAtMixin):
    updated_at: Mapped[datetime] = mapped_column(
        DateTime(timezone=True),
        server_default=func.now(),
        onupdate=func.now(),
    )


def uuid_fk(target: str) -> MappedColumn[UUID]:
    return mapped_column(
        Uuid(as_uuid=True),
        ForeignKey(target, ondelete="FORBID"),
        nullable=False,
    )


__all__ = [
    "Base",
    "CreatedAtMixin",
    "TimestampMixin",
    "UUIDPrimaryKeyMixin",
    "uuid_fk",
]
```

* Preserve the definitions and behavior shown above when reproducing the existing project infrastructure.

Use this mixin when the model requires the standard UUID primary key named `id`.

It provides:

* SQLAlchemy `Uuid(as_uuid=True)`

Do not manually declare `id` when this mixin is inherited.

It inherits `CreatedAtMixin` and provides `updated_at` with:

* `DateTime(timezone=True)`
* `server_default=func.now()`

```python

    status_code=status.HTTP_400_BAD_REQUEST,
    detail="{an appropriate message}",
```

* Do not use this for missing resources or uniqueness conflicts.

## 2. Conflict — 409, Cause Unknown

**Use when:** A database `IntegrityError` occurs and the specific conflict cannot reliably be identified.

```python

    raise HTTPException(
        status_code=status.HTTP_409_CONFLICT,
```

**Rules:**

* Do not claim that a resource already exists unless the cause is known.

**Use when:** The requested resource cannot be found, or the endpoint deliberately treats an inaccessible resource as not found.


* Do not use this for invalid input or conflicts.

**Examples:**

**Rules:**

* Do not use this pattern for every `IntegrityError` automatically.

## 5. Too Many Requests — 429

**Use when:** A client exceeds a rate limit or a request is rejected by rate-limiting rules.

```python

    status_code=status.HTTP_429_TOO_MANY_REQUESTS,
    detail="{an appropriate message}.",

```

**Rules:**

* Replace the placeholder with a concise message explaining the rate limit.
* Preserve the final period.
* Do not use this for ordinary validation errors or unrelated conflicts.

## 6. Forbidden — 403

**Use when:** An authenticated user is not permitted to perform an action under the applicable authorization rules or conditions.

```python

    status_code=status.HTTP_403_FORBIDDEN,
    detail="You are not authorized.",

```

**Rules:**

* Preserve the exact message and punctuation.
* Use this when the user is authenticated but lacks permission to perform the action.
* Follow the existing project's authorization conventions.

## 7. Unauthorized — 401

**Use when:** An authentication endpoint rejects invalid credentials.

```python

    status_code=status.HTTP_401_UNAUTHORIZED,
    detail="Invalid credentials.",

```

**Rules:**

* Preserve the exact message and punctuation.
* Use this template for authentication failures where the credentials are invalid.
* Follow existing authentication and token-handling conventions for other authentication failures.

## General Rules

1. Choose the status code based on the actual cause of the failure.
2. Use these templates instead of inventing a new response convention.
3. Replace placeholders only where permitted; preserve exact fixed messages.
4. Do not catch broad exceptions and turn them into one of these responses merely to suppress errors.

# Unexpected Error Handler Decorator

## Purpose

When asked to create the shared `handle_unexpected_errors` decorator, use the exact implementation below. Do not replace it with a different error-handling approach or introduce additional behavior unless explicitly requested.

## Exact Implementation

```python
from functools import wraps

from fastapi import HTTPException, status


def handle_unexpected_errors(endpoint):
    @wraps(endpoint)
    def wrapper(*args, **kwargs):
        try:
            return endpoint(*args, **kwargs)
        except HTTPException:
            raise
        except Exception as exc:
            raise HTTPException(
                status_code=status.HTTP_500_INTERNAL_SERVER_ERROR,
                detail="An error occurred.",
            ) from exc

    return wrapper
```

## Rules

* Preserve the implementation above when creating the decorator.
* Keep `@wraps(endpoint)` so the wrapper preserves the original endpoint's metadata.
* Re-raise `HTTPException` unchanged so expected HTTP errors retain their status codes and details.
* Convert other exceptions into an HTTP 500 response using the exact status code and detail message shown above.
* Preserve exception chaining with `from exc`.
* Do not add logging, custom exception classes, extra exception handlers, or other behavior unless explicitly requested.
* When applying the decorator to existing endpoints, inspect the current endpoint and preserve its existing behavior and project conventions.
* Do not create duplicate implementations when a shared decorator already exists. Import and reuse the existing implementation instead.

**Core rule:** Use this exact decorator as the project's standard unexpected-error handler.

# Database Configuration Conventions

## Purpose

When asked to create the project's `database.py`, use the exact implementation below.

## Exact Implementation

```python
from collections.abc import Generator

from sqlalchemy import create_engine
from sqlalchemy.orm import Session, sessionmaker

from .config import settings


engine = create_engine(settings.DATABASE_URL)

SessionLocal = sessionmaker(
    autocommit=False,
    autoflush=False,
    bind=engine,
)


def get_db() -> Generator[Session, None, None]:
    db = SessionLocal()

    try:
        yield db
    except Exception:
        db.rollback()
        raise
    finally:
        db.close()
```

* Keep `get_db()` as a synchronous generator dependency returning `Generator[Session, None, None]`.
* Roll back the session when an exception occurs, then re-raise the original exception.
* Always close the session in the `finally` block.
* Do not add asynchronous database handling, connection-pool settings, extra abstractions, or unrelated configuration unless explicitly requested.
* If `database.py` already exists, inspect it before making changes. Do not replace unrelated functionality when the task only requires a specific modification.

# Password Hashing and Verification

## Purpose

Whenever asked to create the project's password hashing and verification functions, use the exact implementation below.

## Exact Implementation

```python
import bcrypt


def hash_pwd(password):
    return bcrypt.hashpw(password.encode("utf-8"), bcrypt.gensalt()).decode("utf-8")


def verify_hash(hashed_password: str, password: str) -> bool:
    return bcrypt.checkpw(
        password.encode("utf-8"),
        hashed_password.encode("utf-8"),
    )
```

## Rules

* Preserve the implementation above when creating the password hashing utility.
* Use `bcrypt` for password hashing and verification.
* Use `hash_pwd(password)` to hash a plaintext password before storing it.
* Use `verify_hash(hashed_password, password)` to verify a supplied password against its stored hash.
* Never store plaintext passwords in the database.
* Never hash a password again when verifying it; use `verify_hash()` instead.
* Do not replace bcrypt with another hashing library or algorithm unless explicitly requested.
* Do not add unnecessary abstractions, dependencies, or behavior.
* If the utility already exists, import and reuse the existing functions instead of creating duplicate implementations.

**Core rule:** Use this exact template for password hashing and verification.
